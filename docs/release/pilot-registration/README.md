## Flow and exact API contract

The marketing page retains one UUIDv4 per selected platform/architecture/release attempt in session storage and navigates to the actual configured n8n **production** form URL with `registration_id` and `platform` query fields. Only those non-contact selection fields go in the URL. No name/email/church details, server credentials or receipt are sent as query parameters. Missing IDs/platforms fail validation; n8n execution IDs are not retry IDs. A deliberate new registration creates a new ID; an error/reload/re-click must preserve the existing attempt.

The n8n Form Trigger 2.2 keeps `registration_id` hidden and presents a required visible `platform` dropdown (Windows, Ubuntu, macOS). Each deployed form belongs to one fixed immutable package and shows its platform, architectures and version **before submission**. The same reviewed nonsecret `deployment-config.json` generates that label and the validator. A submitted OS differing from the displayed fixed package is refused **before reservation or Sheet write**; return to the marketing page to choose that platform. Browser/query artifact IDs, paths, versions or URLs never override deployment configuration.

Both fields use identical `fieldName` and `fieldLabel` values to preserve query/output compatibility; the custom slug uses `parameters.options.path`. No platform is selected by a configured default: the production `platform` query supplies the initial choice. The Test URL does not prove production prepopulation. Both submitted fields remain untrusted and are validated/bound by the API. Retrying a reserved identity uses the same platform and unchanged details; changing normalized details conflicts with its original payload.

Root's earlier isolated n8n 2.45.7 probes established hidden query population, visible platform confirmation and saved/retry completion using synthetic callback/Sheet transports. This private-grant revision requires its own pinned runtime/import and completion/escaping evidence; earlier probes do not establish its behavior. Mocked runtime evidence cannot prove real HTTP authentication, Google persistence, private object reads or live deployment. The documented field/query contract is at [n8n Form Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.formtrigger/).

1. n8n validates display fields and maps to the [v1 normalized contract](../../architecture/api/PILOT-REGISTRATION-v1.md). Final exact fields require product/privacy approval. No account, password, payment or marketing opt-in is added.
2. n8n sends `POST /v1/pilot/registrations:reserve`, `Content-Type: application/json`, with `Authorization: Bearer` using a dedicated **server-only n8n credential**. Body is the normalized contract, including `schema_version: 1`, stable UUID, platform and approved notice ID.
3. For a pending record the response is `schema_version`, `registration_id`, `state: pending` and `sheet_write`: configured `spreadsheet_id`, quoted A1 `range` (for example `'Registrations'!A2:M2`), `majorDimension: ROWS`, `valueInputOption: RAW`, and one `values` array of 13 literal strings. This response contains submitted personal data and is server-to-server, `Cache-Control: no-store`. Never call this endpoint from the marketing browser.
4. n8n performs Google Sheets **values.update**, not append, on exactly that range. The URL is rooted at `https://sheets.googleapis.com/v4/spreadsheets/` and uses `valueInputOption=RAW`. The original payload fingerprint and server-created timestamp determine the identical bytes on every retry.
5. Only after a successful Google response, n8n posts `/v1/pilot/registrations:confirm` with the same server auth. Body: `registration_id` plus `sheet_ack` containing exactly `spreadsheetId`, `updatedRange`, `updatedRows: 1`, `updatedColumns: 13`, `updatedCells: 13`. The stored destination, row and counts must match. The callback trusts authenticated n8n to report the actual Google acknowledgement; a browser-supplied acknowledgement has no standing.
6. Confirmation locks the record and sets its confirmation time once. Response: `schema_version: 1`, UUID, `state: confirmed`, `receipt`, integer Unix `expires_at`. Receipts bind the UUID/platform/pilot channel, intended `pilot-download-grant` audience, issue time and expiry. They contain no contact/church fields. They expire at the earlier of the configured short receipt lifetime and the fixed pilot end; retries do not extend that clock.
7. A repeated reserve for a confirmed same-payload UUID returns the confirmed receipt response and **no Sheet write**. An expired receipt is an actionable `receipt_expired` response, not a new append. P12 must define recovery/refresh deliberately; the operator must not reset IDs to conceal a failed attempt.
8. Both fresh confirmation and already-confirmed retry join `Validate saved receipt`, then call `POST /v1/pilot/downloads:grant` with exactly `{schema_version:1, receipt, artifact_id}`. This request uses a **different dedicated server Header Auth credential** from registration callbacks; no contact/church fields, browser path or caller TTL are sent. P12 verifies receipt purpose/signature and the live confirmed ledger, then resolves the fixed ID in its pinned complete promoted manifest. Wrong OS, missing/expired/revoked build, invalid receipt and missing/failed signer return no URL. Licensed/device download routes remain separate.
9. `Validate private download` accepts only the exact grant schema and configured artifact/release/platform/architectures/checksum/size, exact HTTPS origin and immutable object path, and distinct allowlisted signature query fields. It requires a future integer expiry no later than the original receipt, fixed cohort cutoff and configured maximum of 300 seconds. Unknown/extra fields, redirect/PII query keys, malformed/duplicate query fields and mismatches reach the fixed retry completion. No mutable `latest` fallback or current-time receipt refresh occurs.
10. Success projects only escaped package metadata and the short-lived private read link into Form completion. The receipt/UUID/contact/church data are not passed to completion, HTML fields or query parameters. The link includes provider-required signature fields only. Failed or ambiguous Sheet writes never reach confirmation/grant. The completion is not a redirect and does not auto-download an arbitrary response URL.

The displayed version and fixed artifact configuration must be checked against the same approved P11 manifest/public projection and P14 marketing entry before deployment. The grant response binds release/hash/size/OS/architectures but does not contain a version field; the reviewed deployment mapping provides that display binding. The production form URL is unique to that package deployment. Both macOS public architecture entries may share the same verified Universal artifact/form; do not invent Ubuntu ARM64 or substitute an unsigned macOS package.

Error responses contain fixed `error.code` values (and fixed invalid field names for validation), never submitted values/configuration secrets. Statuses: 404 disabled/unknown record; 403 server auth/receipt invalid; 400 malformed/invalid request or acknowledgement; 409 identity conflict/pending; 410 pilot/receipt/retention expiry; 413 oversized request; 415 non-JSON; 429 throttled; 503 configuration/capacity/database unavailable. Service callbacks have a 32 KiB read limit and a fail-closed throttle. Do not log request/response bodies or Authorization headers at any proxy/n8n/API layer.

## Why retry is safe — and its external constraint

The database stores only a stable UUID, keyed canonical-payload fingerprint, destination fingerprint, assigned row, platform, notice version and timestamps. It does **not** store raw contact/church details. These UUIDs/fingerprints are still pseudonymous data and need the approved owner/policy.

A per-destination allocator is locked during reservation; UUID uniqueness and `(destination, row)` uniqueness are database constraints. Same UUID with changed normalized payload or destination fails with `identity_conflict`. Capacity is bounded by configured rows (maximum 100,000 as an application bound, not a claim about provider limits). Header is row 1; data rows begin at 2. Concurrent same-UUID retries return the same row; different UUIDs cannot collide or silently overrun capacity. Database locks are released before Google calls. The PostgreSQL race tests, not SQLite tests, prove these locking properties.

A Google timeout may mean the write succeeded. **Do not append again or allocate a new ID.** Re-reserve the same UUID and payload, then update the same row and confirm its acknowledgement. Duplicate writes to the same protected row use identical values. If Google/n8n fails before confirmation, the ledger remains pending and no receipt is issued. If the confirmation response is lost, retrying reserve returns the existing confirmed result. Invalid response shapes or HTTP failures go to the retry page, not saved/download success.

**Required protection:** dedicate the tab to this workflow; precreate the configured capacity and exact A:M header. Protect the sheet structure and headers against row insert/delete/reorder/sort and other writers; only the n8n credential should write assigned cells. A manually sorted/deleted/inserted row breaks fixed-row integrity and can overwrite another record even with RAW writes. The configuration gate requires an explicit operator attestation `SHEET_LAYOUT_PROTECTED=true`, but cannot independently prove Google protection. Record evidence before enabling. If structure changes or the ledger/Sheet are independently restored, immediately disable collection and reconcile both; never guess/reset `next_row` or shift historical allocations.

Retention clears contact cell contents **without shifting rows or recycling allocations**. Preserve the minimal allocation ledger/counter at least while any outstanding receipt/attempt could be valid, and document its eventual disposal with the policy owner. After configured retention, attempts/receipts are retired even if the Sheet still holds a row. Clearing/deleting ledger state while collection remains enabled is unsupported: old receipts then fail closed, but resubmission history cannot be reconstructed automatically. Re-enabling after destructive state loss requires a reconciled ledger or a new isolated tab/channel, not ordinary retries. No purge task is silently scheduled by this implementation.

## Deployment configuration — no live defaults

The API is disabled unless `SELAHCUE_PILOT_REGISTRATION_ENABLED=true`. Enabling still fails with `configuration_required` unless all prerequisites are supplied:

| Environment variable | Requirement |
|---|---|
| `SELAHCUE_PILOT_N8N_TOKEN` | Dedicated random server callback token, 32–256 non-whitespace ASCII characters |
| `SELAHCUE_PILOT_RECEIPT_KEY` | Separate random signing key with the same bounds |
| `SELAHCUE_PILOT_FINGERPRINT_KEY` | Separate random keyed-fingerprint key with the same bounds; changing it invalidates existing binding/destination lookup and needs a migration/reconciliation plan |
| `SELAHCUE_PILOT_SHEET_ID`, `SELAHCUE_PILOT_SHEET_TAB` | Actual dedicated document/tab; supported tab characters are letters/digits/spaces/underscore/hyphen, beginning with a letter |
| `SELAHCUE_PILOT_SHEET_ROW_CAPACITY` | Actual precreated final row index including header, 2–100000 |
| `SELAHCUE_PILOT_APPROVED_NOTICE_VERSIONS` | Explicit approved notice IDs; draft/placeholder policy is not approval |
| `SELAHCUE_PILOT_COLLECTION_OWNER`, `SELAHCUE_PILOT_RETENTION_DAYS` | Real responsible owner and approved positive retention days; no values were invented here |
| `SELAHCUE_PILOT_SHEET_LAYOUT_PROTECTED` | `true` only after structural protection and access evidence |
| `SELAHCUE_PILOT_RECEIPT_TTL_SECONDS` | Explicit 30–3600 seconds; a technical short-lived authorization window, separate from the six-month pilot period |
| `SELAHCUE_PILOT_EXPIRES_AT` | Fixed timezone-aware ISO time; owner choice is `2027-04-30T23:59:59Z` |

Use PostgreSQL in deployment, as required by existing non-dev settings. All three keys must differ; no key belongs in source, Vite, form query fields, Figma, Sheet cells or ticket screenshots. Keep Google OAuth in n8n's encrypted server credential store and grant that identity access only to the dedicated spreadsheet. The API does not need a Google access token. A credential compromise invalidates the server attestation trust boundary; rotation/revocation must be rehearsed before live testing. No default Django signing-key fallbacks validate pilot receipts.
