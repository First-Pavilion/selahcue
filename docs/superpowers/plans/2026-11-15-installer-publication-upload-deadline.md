# Task3 shared upload deadline

Root integration clarification, amended after the independent builder check and pending its scoped readback before Task3 assignment. The accepted design's 60-minute deadline applies to the complete upload invocation, including all three objects, authenticated subprocesses, retry delays and anonymous reconciliation. Task2's standalone verifier correctly has a separate 60-minute per-object ceiling. Its current `verify_object_in_child(obj)` interface starts that entire allowance on each call. An upload caller must not accidentally reset its own invocation budget through this interface.

The smallest interface extension is `verify_object_in_child(obj: ObjectPlan, *, deadline: float | None = None) -> VerifiedObject`. The existing one-argument call remains valid. The verifier parent uses the earlier of its own per-object deadline and the caller's original upload deadline, refuses an expired deadline before spawning, and uses that same value through pipe exchange and process completion, checking again before returning success. Reject malformed/non-finite caller deadlines and booleans with code2; an expired valid deadline is code4. No caller can lengthen the verifier's own cap. Cleanup must still kill/reap the owned child after expiry. The child remains credential-free and receives only the unchanged closed object plan. No CLI flag, JSON field, destination override, configurable timeout or new subprocess framework is added. The reconciler's existing one-argument verifier callback can capture the original deadline in a closure; its callable contract need not change.

Task3 creates one upload deadline at entry to `upload_release`, before prepared-release reload, offline AWS executable/model validation, lock acquisition or journal setup. Charge all subsequent local and remote work against that deadline. Check it before and after local stages and at each package/evidence streaming chunk and traversal iteration; acquire the lock nonblocking or with a remaining-budget loop, and cap retry waits by the remaining budget. Pass the unchanged absolute deadline to subprocesses and anonymous reconciliation. Recheck before entering the complete upload-receipt commit and before reporting success. On observed expiry, issue no further remote operation or successful completion; retain available partial/unknown state and clean up owned children. An expired budget cannot justify another PUT or an unbounded recovery probe; a later explicit invocation performs the existing remote reconciliation. Timeouts never prove that a write did not occur.

Synchronous filesystem calls, durable writes, process launch, scheduling and kill/reap are not hard-preemptible. The practical wall bound includes an in-flight operation/cleanup overrun, not a hard real-time return guarantee. Receipt/journal persistence may cross the deadline inside a syscall: preserve truthful durable state, do not claim an on-time successful return, and do not trigger a new remote recovery attempt after expiry.

Task3 additionally owns only the narrow verifier deadline extension and its focused tests in `public_verify.py` and `test_installer_publication_verify.py`, plus an optional internal deadline-check callback on `load_prepared_release` and `hash_regular_file` in `prepare.py`, threaded into their existing evidence traversal and streaming helpers. Existing callers default to no callback; the upload callback raises its existing code4 on expiry. Do not duplicate custody validation, introduce another timer or change the JSON/CLI contract. These are narrow shared-helper ownership additions; other Task1/2 behavior stays unchanged.

Cover an already-expired caller budget (zero child launches), an earlier caller deadline with bounded child termination, a later deadline that cannot extend the verifier cap, malformed/non-finite/bool deadlines, and unchanged one-argument behavior. Add fake-clock controls showing time consumed by reload/hash/model validation reduces the remaining upload budget, expiry during local streaming stops further chunks and remote work, locks/retry waits respect the remaining allowance, and expiry after final verification prevents entering complete receipt commit. Preserve partial/unknown outcomes and assert zero further PUT/reconciliation calls after observed expiry. Reuse Task2's existing process/credential controls and preserve exact error classes and protocol. Source checks qualify synchronous operation/cleanup overruns honestly.

This addresses an integration omission in the original shared-interface preflight, not a failure of the independently reviewed standalone Task2 behavior. Task2 source passes at `bb43af42875bab87c6d1a013feec3c8fa5e5ecb2` remain scoped to that behavior. Task3's resulting composition requires its own independent review. OS scheduling and child reaping remain practical timing bounds, not a hard real-time guarantee.
