# Registration and reset-trace bounds — implementation design

## Registration
Apply fixed global then trusted-source admission before hashing, account queries, writes or mail publication. Defaults:500 registrations/hour globally,20/hour/source, configurable through the established throttle setting format. Both existing and new email paths consume the same admission and return the same refusal shape. The fixed global limit bounds new source-key creation to500/hour; IP scope is included in the existing HMAC-protected IP scope registry, using the fixed unresolved-address sentinel. GraphQL threads the existing trusted client_ip resolver into the service; never trust raw client forwarding headers.

This deliberately retains the repository's conservative global-first/cardinality policy: rejected repeat-source requests may consume global allowance. It bounds expensive work and cache cardinality but does not promise availability against deliberate global-budget exhaustion. A coupled multi-key Redis admission redesign is outside this ticket and must not be invented incidentally.

Registration fails closed with an existing safe coded refusal when shared admission cannot be established. Do not hash, query, write or enqueue mail during a limiter outage. No generic fail-open bypass and no unbounded process-local signup table. Preserve ordinary invalid-input validation and existing signup semantics after admitted requests; errors must not disclose whether an email exists. Configuration values and outage/rollback behavior must be documented.

Security preflight ruling: use SafeAPIError(ErrorCode.RATE_LIMITED) for registration budget refusal and STORE_UNAVAILABLE. The existing GraphQL error handler suppresses this safe code; introducing a different ordinary code can reach Strawberry's per-error logger and expose inline signup literals. Cover both conditions with real inline-literal GraphQL requests and captured logs, plus identical existing/new refusal bytes. This keeps the established safe error handling path without widening logging behavior.

## Named reset-confirm traces
Retain existing anonymous global and per-account budgets. Add a separate named-outcome aggregate scope, default6000/hour across processes; outage fallback600/hour/worker. Fixed aggregate key first, then per-account accounting; this bounds cardinality of new named-account cache keys and conservatively spends aggregate allowance on later per-account refusals. Neither budget alters reset response, token state, password policy or success audit. Aggregate exhaustion reports a fixed reason through existing bounded once-per-minute suppression reporting; no new raw email/token/IP logging. Anonymous exhaustion must not consume this separate named allowance.

If the source throttle already established STORE_UNAVAILABLE, do not retry the shared cache during trace accounting. Existing local-only protection is reused, with the new aggregate ceiling applied.

Security preflight correction: _SuppressedTally retains only the first detail in an interval. Add a constant-size aggregate-cap-hit boolean to its existing locked state and OR it on every aggregate skip, even when the first reason was per-account. Include a fixed aggregate-cap marker in the next emitted minute summary and clear it with the same atomic interval reset. A fake-clock mixed-reason regression must prove that an earlier non-aggregate skip cannot hide the overall-cap alarm. Preserve bounded summary cadence and data minimization.

## Outage account table
Preserve all unexpired incumbent windows under its lock; reclaim expired windows before admitting new identities. Never evict an active incumbent to admit a fresh identity. Distinguish accepted, tracked-account-exhausted and capacity-overflow outcomes. Overflow routes to the existing shared outage ceiling; it does not create an account entry or grant a fresh independent allowance. Tracked exhaustion never falls back to overflow. Avoid nested table/ceiling locks (or specify one consistent order), preserve bounded memory and existing reset behavior.
