## 6. Capacity arithmetic and policy agreement

Under global-budget and pool locks, occupancy is COUNTED external resource rows in that pool plus HELD claims with no linked resource. A COUNTED claim is represented by its resource once, not added again. Released claims without resources add zero; released claims pointing to a still-COUNTED resource do not remove that resource. Externally inventoried resources are inserted COUNTED even without local mapping. Partial inventory observations may add conservative COUNTED presence immediately; only a completed fresh scan can enable admission.

A successful create binds resource and claim atomically under pool/claim locks. Inventory may safely deduplicate a known external ID against an existing resource. For a still-unknown create, exact-marker candidate must be unique across the completed scan, within the same immutable parent, and compatible with all known stage IDs; mark it as candidate before associating. Only recovery under org/mapping locks establishes identity/links claim, and in that transaction occupancy removes the unknown hold and counts the resource once. Until then double-counting candidate plus hold is conservative, not permission to release uncertainty. Conflicting duplicate marker/cross-owner IDs stop automatic binding. No completed scan erases a previously counted resource. Only RESOURCE_EXCLUSION evidence changes COUNTED->EXCLUDED; restored positive observation changes EXCLUDED->COUNTED and records new evidence/audit. Mapping state never drives occupancy.

New allocation requires `occupied + 1 <= capacity - reserve`. Sum rate rows per global provider and parent pool: `HELD + DISPATCHED with dispatched_at > at-window` (3600 or86400 seconds); at exact boundary old dispatch leaves the rolling window. Before reserving initial stage tokens require sums+1 DG or+2 OA <= each positive cap. Before dispatch, moving its own HELD row to DISPATCHED preserves sum but recheck current limits, including any other holds and tighter current epoch. A proved-not-created retry releases no dispatched token; reserve a fresh hold within all four caps. Disabled/zero/absent policy cannot be treated as unlimited.

Pools missing complete inventory, with `at >= inventory_valid_until`, or with nonmatching scope epoch fail POLICY_UNCONFIGURED. Completed scan freshness is `started_at + 300s`, not finish+300: a multi-page scan older than300s at completion is retained as evidence but cannot authorize admission. Refresh due every60s; only one PARTIAL scan per pool. Never publish a stale scan over a newer current epoch. Failed/partial scans do not extend freshness. No claim of atomic provider snapshots or absence-finality is made.

## 7. Lock order and transactional service flow

Order: **org -> exact licence -> exact device -> exact token -> ledger weeks/reservations if later integrations need them -> global provider budget -> parent pools sorted(provider,parent) -> demand -> mapping -> claim -> stage -> attempt -> allowance -> outbox**. No Task4 ledger writes. Registry calls may reacquire the already-held org/mapping lock, never introduce an earlier new org. Multiple mappings within one org sort by UUID; avoid multi-org transactions. Inventory/policy paths lock only global/pool/scan/resource-side rows and never subsequently take org/demand/mapping; their work is separated from recovery binding. Outbox-only publisher transactions never call provisioning while locked. Existing licence->device/token legacy writers do not acquire org afterward on these paths; keep new shared eligibility pure.

`ensure_provider_ready` rejects invocation inside an existing atomic block: it owns its bounded transaction. Lock original identity rows separately with only needed fields (no token hashes/fingerprints). Resolve provider's budget/pools and current owner/demand without locks only to plan lock order; then lock/re-read. Sample clock after every required lock. Verify facts/current allowance and local public admission. An eligible ACTIVE owner returns ReadyMapping before create-budget/inventory gates. Existing PROVISIONING owner returns its UUID pending; no new outbox/claim/token reservation per poll. Original demand identity remains immutable; current caller eligibility does not rebind its worker trigger.

With no owner and no permanent demand, lock candidate published pools in deterministic order, re-evaluate capacity/limits and choose the first admissible matching scope. Insert demand, mapping (registry begin_mapping with fixed `provider-provisioning-intent` actor and exact controls_evidence_ref), claim, stage(s), held allowance rows, first PREPARED attempt and PROVISION outbox in one transaction. Registry begin sees caller-owned outer atomic. If no scope succeeds return stable code precedence DISABLED, POLICY_UNCONFIGURED, RESOURCE_CAPACITY, DAILY_CREATE_LIMIT, HOURLY_CREATE_LIMIT; malformed/eligibility/allowance use ProvisioningRejected. No mutation remains after failure. No broker/network call in request path.

An existing FAILED/RETIRED permanent demand is never recreated by poll. Eligible calls return ProvisioningRejected(OPERATOR_REQUIRED), preserving root-chain cap. WAITING_CAPACITY after confirmed cleanup returns Pending on its retained latest mapping UUID and may schedule idempotent replacement work; it has no readiness ETA. No new quota/resource claim is created until capacity actually passes.

## 8. State transitions, bounded recovery and cleanup

Attempt legal edges (same-state metadata updates only within allowed lease/receipt rules): PREPARED->DISPATCHED or CANCELLED; DISPATCHED->SUCCEEDED, DEFINITE_FAILURE, OUTCOME_UNKNOWN; OUTCOME_UNKNOWN->RECOVERING or OPERATOR_REQUIRED; RECOVERING->OUTCOME_UNKNOWN, SUCCEEDED, DEFINITE_FAILURE, OPERATOR_REQUIRED; OPERATOR_REQUIRED->RECOVERING only after new explicit operator evidence; terminal states do not reopen. For cleanup operations only, exact PROVIDER_CLEANUP_CONFIRMED proof also permits OUTCOME_UNKNOWN/RECOVERING/OPERATOR_REQUIRED->SUCCEEDED through the locked confirmation service below. A compatible late complete response may transition OUTCOME_UNKNOWN/RECOVERING/OPERATOR_REQUIRED->SUCCEEDED; this resolves the attempt only, not automatic mapping activation. Lease expiry transitions DISPATCHED->OUTCOME_UNKNOWN and RECOVERING->OUTCOME_UNKNOWN, clears lease, retains all facts and consumed token. It never creates another POST attempt. Late complete response receipt can add safe missing identity fields to original attempt regardless of lease; it cannot overwrite conflicting IDs, binding or cleanup intent.

Stage legal edges: READY->WORKING or CANCELLED; WORKING->DONE,READY,BLOCKED,CANCELLED; BLOCKED->READY only for project-success dependency, current capacity re-evaluation of an unsent retry, or explicit recovery evidence; DONE/CANCELLED terminal. Exact operator-confirmed cleanup adds BLOCKED->DONE for a cleanup stage whose current unresolved attempt is confirmed, without ever setting READY or dispatching another mutation. WORKING->READY requires prior attempt DEFINITE_FAILURE with positive non-creation proof and attempts<3. Third proved-not-created result blocks stage and sets chain FAILED; no resource replacement is inferred from a failure with no key. Unknown never becomes READY. A completed create can set stage DONE while chain remains RECOVERY_REQUIRED because its secret was not safely stored.

Normal chain edges: QUEUED->WORKING; WORKING->READY after registry activation; QUEUED/WORKING->RECOVERY_REQUIRED for unknown/secret-loss; QUEUED/WORKING->FAILED after definite ineligible/no-create or retry exhaustion; RECOVERY_REQUIRED->WORKING on safe same-chain continuation, ->WAITING_CAPACITY after completed cleanup/retirement, or ->FAILED for exhausted/unresolvable operator-required work; WAITING_CAPACITY->QUEUED on one approved automatic replacement; READY->RETIRED on explicit audited retirement. Recovery resolution may move FAILED->RECOVERY_REQUIRED only via newly supplied operator evidence and without changing trigger/replacement count. Registry states remain separate and strictly use Task3 services.

Claim transitions: HELD->COUNTED on known allocation; HELD->RELEASED only positive whole-allocation non-creation evidence and no unresolved create; COUNTED->RELEASED only resource exclusion proof. RELEASED never reopens; unexpected later allocation stays a COUNTED external resource, identity conflict is alerted, and no historical row is erased. Allowances HELD->DISPATCHED or RELEASED; both terminal. Canceling a stage releases only its undispatched HELD rows. After a project succeeds but service stage cannot run, its project stays counted; releasing service-stage token is not releasing project capacity.

Recovery schedule: first metadata round due5s after unknown, second30s, third120s, all relative to original unknown instant stored as `next_action_at` progression; add `unknown_since:TS?` to attempts, immutable once set. Increment recovery_round when starting a new complete round, not each page. Each round is bounded by10000 pages and300s elapsed; exceeding either gives OPERATOR_REQUIRED with partial evidence, no absence proof. A transient read/child failure ends that round without completeness and schedules next, or operator after third. If a prior round finishes after the next scheduled offset, use max(current post-lock time, unknown_since+next offset); do not run rounds concurrently. One page/request per invocation. Repeated cursors, invalid pagination, ambiguous candidates, missing necessary IDs or inconsistent owner are unresolved, not definite failure. Empty complete enumeration cannot prove non-creation. Operator evidence can record provider-confirmed non-creation and release or permit remaining bounded retry, never reset stage sequence. It must match exact original parent/attempt/identity.

Project recovery matches exact persisted marker in configured parent, unique across full scan, with compatible creation timestamp no earlier than dispatched_at minus one second (provider timestamps may be integral). If timestamp is absent or incompatible, require operator evidence before binding. DG key recovery uses comment; OA account uses name under the already-bound project; key recovery matches exact returned service-account owner ID. A unique candidate can bind provisional positive identity and deduplicate capacity but **does not establish cleanup ownership** merely by its mutable label. Cleanup ownership needs a recorded valid create receipt carrying exact IDs or explicit OWNERSHIP evidence. PROVIDER_CLEANUP_CONFIRMED proves the recorded exact cleanup outcome; it does not replace the ownership/authorization evidence required before the original dispatch. Never infer a key ID from a secret, redacted key, service-account ID, project ID or tag.

A missing/lost one-time secret cannot activate. If exact target ownership and current lifecycle authorization exist, orchestrator first commits cleanup stages and `cleanup_started_at:TS` on the claim (add nullable field; once set immutable), blocking any later activation. DG chain: revoke exact key; OA chain: revoke known exact key if known, delete known owned service account if known, then archive owned project. No skip of an unknown dispatched service-account create to pretend project cleanup is complete: resolve it/obtain explicit ownership evidence first. An OA project-only failed chain can archive its known owned project without inventing an account/key. Stages are sequential, each targeted operation one durable attempt/request. A validated successful exact-target cleanup response marks attempt SUCCEEDED/stage DONE, stores CLEANUP_SUCCESS with exact operation/targets, binds cleanup_completion_evidence and invokes the common cleanup-completion consumer below. Authoritative operator confirmation of an unknown cleanup instead stores distinct PROVIDER_CLEANUP_CONFIRMED and uses that same consumer without another HTTP mutation. Unknown cleanup is inspected; absent list item alone does not prove it succeeded. A still-present listing alone does not establish a definitive prior outcome. Unknown/denied cleanup stays blocked after bounded inspection and requires operator evidence; do not automatically issue a second DELETE/archive. A positively proved LOCAL_NOT_SENT cleanup failure may retry with a new sequence up to three attempts. Create-token budget is unaffected because cleanup is not creation. This uses the same positive-non-dispatch retry edge, not a new interpretation of list absence/presence.

Only after every required cleanup stage is DONE may registry retire the mapping and set chain WAITING_CAPACITY. Claims/resources retain consumption unless independent counting evidence excludes them; OpenAI archive never automatically frees a slot. At most one replacement is allocated: under original org/identity/global/pool locks verify original demand still eligible with allowance, replacement_count=0, cleanup completion and new current capacity; increment replacement_count to1, create new mapping/claim generation1 + fresh create stages/tokens/outbox atomically. Replacement may select another currently admitted parent by ordinary sorted capacity selection; it is a new resource chain, never reassignment of old mapping. Further failures at generation1 cannot create another mapping, even after polls or new token authentication. If no capacity, WAITING_CAPACITY remains with no speculative holds. If original trigger becomes invalid, set FAILED and retain cleanup/history. Known-resource recovery and authorized cleanup do not require customer eligibility; creates and replacement always do. Provisioning=false permits metadata recovery and already-authorized cleanup, never new creates/replacements.

### Exact operator confirmation and shared completion consumer

`confirm_provider_cleanup` is implemented in `providers/provisioning.py`. It requires initialized role provisioner **and** initialized entrypoint operator, valid `ProvisioningAuditContext`, positive pool ID, canonical UUID objects, operation in CLEANUP_OPS and a validated partial identity. Its identity fields are an **exact tuple**, including nulls, not the registry's additive patch semantics: scope must equal the pool/provider/parent; project/service-account/key fields must equal the referenced cleanup stage's immutable targets, including the stage's retained contextual IDs. No target is inferred or completed from operator prose. The API accepts only nonsecret IDs/evidence references and performs no HTTP, broker call or credential mutation.

Resolve the immutable org/chain references read-only, then lock in the existing order: org -> global budget -> pool -> demand -> mapping -> claim -> **all required cleanup stages ordered UUID** -> current attempts ordered UUID -> relevant outbox rows. Customer licence/device/token locks and current allowance checks are omitted because this records recovery truth rather than creating new work. Re-read every relationship after locking and sample clock afterward. Require the attempt to be the stage's current attempt, its stage/claim/mapping/demand/pool chain to agree, dispatch_started_at and cleanup_started_at to exist, and the dispatch scope epoch plus persisted ownership evidence to establish that the original exact-target cleanup had lifecycle authority. Require the parent still be configured in this operator runtime. Current provisioning/public flags, expired triggering token or removed current cleanup permission do not erase a confirmed historical result; this path authorizes no new provider mutation. Subsequent remaining cleanup dispatch still needs its current lifecycle authorization, and replacement still needs all normal new-work gates.

Admit OUTCOME_UNKNOWN, RECOVERING or OPERATOR_REQUIRED. A still-DISPATCHED attempt with a live lease is refused OPERATOR_REQUIRED; an expired DISPATCHED lease first follows the normal OUTCOME_UNKNOWN transition under these same locks, then may be confirmed. PREPARED, CANCELLED or DEFINITE_FAILURE are refused INVALID_CONTEXT; a create operation is always refused INVALID_CONTEXT. For SUCCEEDED, accept only corroboration/replay of a cleanup completion already tied to matching exact-target CLEANUP_SUCCESS or PROVIDER_CLEANUP_CONFIRMED. Never overwrite an incompatible terminal outcome or bind an unrecognized attempt merely because an external ID matches.

Before insertion check the operator request key and existing confirmation for this attempt. Exact replay means matching kind, operator_id, request_id, evidence_ref, pool/mapping/attempt, operation and every identity field; return its immutable evidence ID with replayed=true after re-running the idempotent completion consumer. Reusing `(operator_id,request_id)` for different facts, or trying to replace this attempt's existing operator proof with a different request/operator/reference/identity, raises IDENTITY_CONFLICT with no changes. On the first accepted confirmation, insert immutable PROVIDER_CLEANUP_CONFIRMED evidence with observed_at=the post-lock instant. A previously response-completed attempt may receive this one corroborating proof but retains its original CLEANUP_SUCCESS pointer and completed_at; return replayed=false for that first proof. Unique races are settled by rollback and the same exact comparison, never an overwrite. Caller-supplied observed times, provider response bodies and free-form success booleans are not accepted.

For a newly resolved unknown, set attempt SUCCEEDED, completed_at=the post-lock instant, cleanup_completion_evidence=new evidence ID, clear lease/next_action_at/error_code, set stage DONE, and cancel that attempt's pending/sent recovery outboxes. Keep dispatch time, operation, targets, recovery history and all capacity accounting unchanged. A late worker receipt may add compatible safe metadata but cannot re-open the attempt, change the completion proof or send another mutation. Record the evidence, transition, finite metadata audit and completion-consumer effects atomically. If a chain is FAILED with last_error_code in {CLEANUP_UNKNOWN, OPERATOR_REQUIRED} because this still-unresolved cleanup blocked it, new authoritative evidence takes the already-permitted FAILED->RECOVERY_REQUIRED edge before evaluating completion; no trigger/count reset.

The private `finish_cleanup_locked(claim_id:UUID, *, at:datetime)->ChainState` consumer is called inside that same lock-owning transaction by **both** validated response finalization and operator confirmation. It takes no new earlier-order locks and performs no HTTP/broker operation. Add `cleanup_required_operations:JSONField|null` on ProviderResourceClaim: at cleanup start, persist the exact ordered finite operation array (DG revoke only; OA known-key revoke if required, known-account delete if required, archive), create all those stage rows atomically, and set cleanup_started_at. This list is nonempty, maximum3, duplicate-free, immutable thereafter, and null iff cleanup_started_at is null. It excludes no previously dispatched unknown account/key stage by guessing that resource absent. DB shape checks plus service/PostgreSQL history guard enforce this frozen plan.

The consumer verifies that actual cleanup stages equal that frozen list, every required stage is DONE, and every corresponding current attempt is SUCCEEDED with an exact matching completion proof of one of the two cleanup kinds. Before changing demand state, if this is an already-retired generation0 claim and demand.current_mapping points to its valid generation1 successor, verify replacement_count=1 and the successor previous_claim link, then return the current demand state without scheduling work or changing either chain. This preserves progressed/replaced/terminal demand state on a replay of old proof. Also return unchanged when the confirmed mapping is already RETIRED and its current demand is FAILED or RETIRED for a later terminal reason (including INELIGIBLE or RETRY_EXHAUSTED); replay must not turn that demand back into WAITING_CAPACITY or recreate a replacement outbox. If some required stage is unfinished, retain RECOVERY_REQUIRED, create/reuse a PROVISION outbox for the next permitted unsent cleanup stage, and return; unresolved stages schedule only their existing bounded recovery. If all are complete, retire a still-PROVISIONING/ACTIVE mapping through the existing audited registry service, set demand WAITING_CAPACITY for generation0 with unused replacement allowance, and create/reuse its PROVISION outbox **in this transaction** so the worker performs the already-frozen replacement gates later. A generation1 chain has no remaining replacement: retain terminal history and set FAILED with RETRY_EXHAUSTED, creating no replacement outbox. If a generation0 claim already has replacement_count=1 but no consistent successor, refuse IDENTITY_CONFLICT rather than reset the count or create another chain. A mapping already RETIRED with the matching completed plan is an idempotent local no-op; incompatible registry state refuses IDENTITY_CONFLICT. No proof or completion timestamp is rewritten on replay. Sweeper also detects a complete frozen cleanup plan with unfinished local finalization and schedules the same PROVISION consumer, so crash/replay cannot strand a confirmed cleanup.

Completion does not set resource EXCLUDED, release a claim, refund a create token, reset the original trigger, increment/reset retries, or bypass replacement_count. In particular, PROVIDER_CLEANUP_CONFIRMED for OA_ARCHIVE_PROJECT never frees OpenAI capacity; RESOURCE_EXCLUSION remains the only separate counting proof. OWNERSHIP, PROVIDER_NONCREATION, list absence and RESOURCE_EXCLUSION cannot mark cleanup DONE. Confirmation is authoritative operator evidence of the exact dispatched operation, not a proxy for another mutation or a per-church normal-success approval.

Imported Task3 ACTIVE mappings need no demand/claim to be reused. Inventory counts their resources externally; Task4 must not fabricate triggering demand or automatically retire/replace an imported mapping. Operator lifecycle beyond this exact Task4-created chain is not implemented here.

## 9. Outbox, task discovery, sweep and cancellation

`providers/tasks.py` imports the five @shared_task entrypoints from provisioning_tasks.py; imports themselves do not initialize role or read credentials. Names: `providers.provision`, `providers.recover`, `providers.inventory_page`, `providers.publish_outbox`, `providers.sweep`. Every route targets only `provider_provisioning`. Set ignore_result=True, acks_late=True, reject_on_worker_lost=True, max_retries=0 (no automatic Celery retry of business operations), soft_time_limit=15, time_limit=20. Worker boot retains Task3 queue/role enforcement. Each task checks initialized provisioner role before DB, frame parsing or network. Queue registration is tested in a fresh interpreter using actual autodiscovery.

The first three tasks accept exactly `outbox_id:str`; they parse canonical UUID and load the DB subject. Publish task accepts exactly `outbox_id:str`; sweep has no arguments. No mapping/provider/URL/body/credential supplied by a broker message overrides DB authority. Outbox payload is JSON `{"outbox_id":"<UUID>"}`. Broker task_id is outbox UUID for visibility only, never relied on for deduplication. A worker validates kind/name agreement and subject relations before accepting it.

Outbox edges: PENDING->PUBLISHING under lock, set UUID lease until at+30; commit/close every DB connection; call one fixed Celery task with `retry=False`, queue override and ignore_result=True. Existing broker connect/socket limits remain finite and no publish retry loop is enabled. On success reacquire outbox-only lock, sample time and set SENT/sent_at, clear lease iff publisher lease still matches; on failure set PENDING/available_at=at+5/error, clear lease. Crash/timeout leaves PUBLISHING for sweep to reclaim. Worker may ACK before publisher saves SENT: ACKED wins and publisher never overwrites it. PUBLISHING->ACKED and SENT->ACKED are both valid. ACKED/CANCELLED terminal. Duplicate valid worker delivery of ACKED row observes existing state and does not call transport again.

Worker admission transaction locks subject in the ordinary order, then outbox, ACKs when it durably claims dispatch/scan/recovery or observes already-completed/canceled work. Claiming external operation sets its own durable lease before commit. ACK alone cannot be the only progress record. If eligibility/capacity temporarily pauses a PREPARED stage, ACK its delivery and leave next_action_at for sweep. On invalid subject/name, cancel row, fixed INTERNAL_FAILURE audit, no provider request. A valid ACKED delivery whose subject is still progressing returns without transport; only a fresh generation scheduled from durable due/lease state may claim the next step.

Beat adds only `providers.sweep` every5 seconds, routed explicitly to provider_provisioning; maintenance beat never loads policy/credentials. Sweep uses maximum100 candidates total per invocation and a15-second monotonic work budget, stopping before another candidate when elapsed budget is exhausted. Each candidate uses one small transaction; interrupted work rolls back that candidate, not already committed progress. It checks due PREPARED attempts, expired dispatch/recovery leases, due recovery rounds, incomplete scans with expired leases, ACKED tasks that crashed before progress, and pools due inventory refresh. It creates/reuses pending outbox rows under subject lock. It requeues PUBLISHING expired or SENT without ACK after30s. Terminal/canceled subjects cancel obsolete outboxes. Active operation lease prevents concurrent external dispatch. Sweep creates no provider HTTP requests.

For broker publication, sweep selects at most20 due outboxes within that overall100 budget, closes DB and calls `publish_outbox` one at a time; each call makes one broker attempt. A hard-killed publisher leaves its durable30-second lease recoverable. No business task is dispatched inside transaction.on_commit (which is neither durable nor a separate worker). The sweep itself comes from beat; losing one sweep message loses no durable demand. Cancellation racing publisher may cause a stale delivery; worker checks canceled subject and refuses work. Broker-side messages need not be revoked/deleted.

Inventory refresh: when `clock >= scan.started_at+60s` of last completed/failed scan and no PARTIAL exists, sweep creates PARTIAL scan for current published scope epoch and one page outbox. First publication does the same. A page task claims scan lease30s, commits and closes DB; one GET; records items/cursor in a new transaction. Nonterminal page creates next generation outbox. Terminal page sets COMPLETE only if the response/schema/pagination are valid and scope epoch still current; it publishes latest_complete_scan and valid_until=scan.started_at+300s. If a newer epoch was published, scan becomes FAILED with POLICY_MISMATCH, observed positive resources retained and no freshness advance. Duplicate pages after lost ACK use item uniqueness and expected page_number/cursor; no second advance. The immutable requested cursor/page fields already specified on each INVENTORY_PAGE outbox ensure a stale page receipt cannot apply to a later cursor. A failed page/lease expiry retries that same page as a read through a new generation, at most three tries; add `page_retry_count` 0..3 to scan reset on successful page. Exhaustion fails scan. New scan remains a future read, not create authority.

Wire protocol is one unsigned four-byte network-order length plus UTF-8 strict JSON frame each direction, schema_version1 and exact fields. Input object exactly `{schema_version, provider, parent_scope_id, method, path, query, body, credential_b64, absolute_timeout_ms}` with method from GET/POST/DELETE, path/query/body privately constructed allowlists revalidated by child, canonical base64 credential bounded4096 bytes, absolute_timeout_ms<=9000. `parent_scope_id` is required for both providers, populated only from the already equality-checked request.scope and credential.scope, never from HTTP/customer input or a credential-byte interpretation. The child independently validates provider membership and the parent as a true str of1..256 printable non-space ASCII characters (Task3 Id grammar), rejecting missing/null/unknown fields before constructing HTTP. For OpenAI it constructs the single fixed `OpenAI-Organization` header from this field alone; neither the path nor opaque key supplies an organization fallback. For Deepgram it percent-decodes the one canonical parent path segment exactly once, requires byte-for-byte equality with parent_scope_id, and requires canonical re-encoding to reproduce that segment. An absent, malformed or mismatched parent fails VALIDATION/before_http. The child receives no arbitrary header map and imports no config/environment to fill a scope. Total input<=16384 bytes. Transport failure codes are exactly VALIDATION, SPAWN_FAILURE, INPUT_PROTOCOL, CONNECT_TIMEOUT, READ_TIMEOUT, ABSOLUTE_TIMEOUT, RESPONSE_TOO_LARGE, RESPONSE_PROTOCOL, TRANSPORT_FAILURE. Output object is exactly one of `{schema_version:1,kind:'response',status:int,request_id:str|null,body_b64:str}` or `{schema_version:1,kind:'failure',phase:'before_http'|'possible_dispatch',code:<finite transport code>}`; mutation body decoded max1MiB, read max4MiB, corresponding framed output bounded6MiB. Output frame contains secret-bearing provider create response only in pipe memory; parent immediately parses to typed redacted DTO, discards raw buffers and never persists/logs them. No generic transport frame serialization outside this private seam.

Parent checks all DB aliases are closed before starting child. Parent monotonic deadline covers spawn, input write, DNS/connect/read through child, output framing and cleanup: total10s, child budget at most9s leaving1s for cleanup. Pipes are nonblocking; selectors multiplex partial write/read with remaining deadline. Never `.communicate()` without a bounded timeout; never wait for EOF beyond the frame/deadline. Child uses stdlib http.client + TLS, connect2s/read5s shortened to remaining child deadline; it verifies content-length/body bounds while reading bounded chunks, refuses non-2xx redirect following and returns status safely. DNS/slow trickle can stall child but parent kills its process group at child deadline, including any descendant; child code launches none. No background thread is used. Parent SIGKILLs on protocol/error/deadline, closes pipes and waits only within the final cleanup budget. If kill/reap cannot finish within10s, terminate the Celery task process via fixed exit78 rather than continue/leak authority; durable DISPATCHED remains recoverable. OS-level uninterruptible process states are not a success or recoverable credential; local tests must demonstrate ordinary timeout/kill/reap behavior. No source claims a kernel can be forced to schedule before a deadline.

If parent never sends a complete valid input frame and child confirms before_http/no HTTP construction, LOCAL_NOT_SENT may be returned. Any uncertainty after child input handoff is MutationUnknown, even if no response bytes arrived. Task wrapper captures its20-second hard deadline on entry. Before marking DISPATCHED/starting transport it requires at least12 seconds remaining; otherwise it leaves PREPARED/due or moves already-durable dispatch to unknown without calling the child. HTTP response parsing and secret handling complete before parent transaction B, within worker hard20s; long DB waits are guarded separately by lock timeout below. Child live transport is unreachable in synthetic tests unless explicitly selected; tests use a loopback-only fixed harness for deadline/framing process tests without credentials/provider endpoints. Production transport does not accept that test URL override.
