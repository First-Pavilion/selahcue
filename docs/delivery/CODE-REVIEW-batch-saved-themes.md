## What shipped

A **saved-theme library** persisted across the stack:

- **Store (controller).** `LiveController` holds `saved_themes: BTreeMap<String, String>` (name → **canonical** theme_json) + a `saved_themes_dirty` flag. `Command::SaveTheme{name, theme_json}` trims + bounds the name (`MAX_THEME_NAME_LEN=64` bytes), deserializes the JSON to a `Theme` and stores the **canonical re-serialized** form (never the raw wire bytes), and rejects a NEW name past `MAX_SAVED_THEMES=256`; `DeleteTheme{name}` removes. `saved_themes()` / `take_saved_themes_dirty()` / `mark_saved_themes_dirty()` / `load_saved_themes()` (startup; drops invalid/over-cap without dirtying). `operator_view()` reports the library.
- **Wire + RBAC.** Additive `Command::SaveTheme` / `Command::DeleteTheme`; `OperatorStateView.saved_themes: Vec<SavedThemeView{name, theme_json}>` (serde `default` + `skip_serializing_if="Vec::is_empty"`, so the pinned v2 fixtures stay byte-identical when empty). Both commands map to `ConfigureOutputs` (Operator-only) in `rbac.rs`.
- **Persistence.** Migration **v11** `CREATE TABLE saved_theme(name PRIMARY KEY, theme_json)` (`target_version()==11`, append-only; an older DB opens and starts empty). `saved_theme_repo` `save_all` (DELETE-then-INSERT in one transaction, so a delete-in-memory becomes a delete-on-disk and a crash mid-write never leaves a partial library) / `load_all` (ordered by name). The desktop loads on startup (`c.load_saved_themes(store.load_saved_themes())`, config not session-state so it loads on clean/crash paths too) and saves on `take_saved_themes_dirty()` in the autosave loop + the clean-exit flush (re-arms the flag on a failed write; skipped on critical-disk / clean-mode).
- **Frontend (Theme Designer).** "Save changes" opens an **inline name form** (no `window.prompt` — WKWebView blocks it); the template list shows **built-ins (read-only, tagged)** + **saved themes (load on click, delete via a two-click ✕ confirm)**, wired to host `save_theme`/`delete_theme`; `syncSavedThemes` folds `view.saved_themes` into the list on each 1s poll (guarded so a focused save-name field is never clobbered). New `#[tauri::command]` `save_theme`/`delete_theme` wrappers + `OperatorShell`/`RemoteOperator` methods. Import/Export a theme FILE stay honest "later" affordances (contract non-goal).

## Findings and dispositions

| # | Lens | Sev | Finding | Disposition |
|---|------|-----|---------|-------------|
| 1 | frontend | **MED** | **Fake success on a host-denied save.** `tdDoSave` announced "Saved …" (aria-live) purely on the invoke **promise resolving** — but a host-side **DENY** is not a rejection: both backends (`OperatorShell.act` discards the reply; `RemoteOperator.act` treats `Denied` as non-error) return `Ok(unchanged view)`. A theme named in a non-Latin script (e.g. ~30 CJK chars = ~90 **bytes**) passes the client `maxlength="64"` (UTF-16 code units) but the host rejects it (90 bytes > the 64-**byte** `MAX_THEME_NAME_LEN`). The operator was told it saved when it did not, with `tdSelected` left pointing at an absent name. (Same path for the 257th theme at the cap.) | **Fixed:** `tdDoSave` now (a) rejects a name whose **UTF-8 byte length** exceeds 64 *before sending* (`tdNameBytes` via `TextEncoder`, with an `encodeURIComponent` fallback for WKWebView), matching the host cap exactly; and (b) claims success only after **verifying the returned view actually contains the name** (`v.saved_themes.some(t => t.name === name)`), else reports "Couldn't save … — the name may be too long or the library is full." Verified headlessly (a 90-byte CJK name is rejected client-side, form stays open). |
| 2 | frontend | **MED** | **Two-click delete confirm defeated by a mid-confirm list rebuild.** The armed state lived on the DOM button (`✕?` + `.confirm`) but the gate was the module var `tdConfirmDel`, which `tdList()` never reset on rebuild. Any rebuild during the 3 s window (selecting another template, or a poll-driven `syncSavedThemes` on a concurrent change) recreated the ✕ **unarmed** while `tdConfirmDel` still held the name → the next single click deleted with **no confirmation**. | **Fixed:** `tdList()` now clears `tdConfirmDel = null` at the top of every rebuild, so an armed delete can never survive a re-render invisibly — a post-rebuild click re-arms instead of deleting. Verified headlessly (arm → select a built-in → the ✕ is disarmed → a single click re-arms; the theme survives). |
| 3 | frontend | LOW | **A saved theme sharing a built-in's name → duplicate rows + dual `aria-pressed`.** Selection was keyed by bare `name`, so saving a theme called "classic" put two "classic" rows in the list; selecting either set `tdSelected="classic"` and **both** rows reported `aria-pressed="true"`; and the Save pre-fill (`isSaved = tdSaved.some(t => t.name === tdSelected)`) then targeted the saved copy even when the built-in row was selected. | **Fixed:** selection is now keyed by **kind** (`tdSelectedKind`: `builtin`/`saved`/`""`) alongside the name, so exactly one row highlights and the Save pre-fill only fires for a selected **saved** theme (a built-in never pre-fills → Save = save-as-new, no silent overwrite). Verified headlessly (one row pressed on collision; built-in selection pre-fills empty). |

### Caught by the batch's own headless render (not the review) — fixed

- **Serialization shape mismatch.** The internal `OperatorView.saved_themes` was `Vec<(String, String)>`, which serde serializes as `[["name","json"]]` (array-of-tuples) — but the Theme Designer reads `view.saved_themes[i].name` / `.theme_json`. The Tauri `view` command returns this **internal** view, so the real webview would have received `undefined` names. (The initial headless harness masked it by stubbing `{name, theme_json}` objects; the mismatch surfaced when reconciling the stub with the real type during the finding-1 fix.) **Fixed:** the internal view now uses `Vec<SavedThemeView>` (identical to the wire type), so local + remote + webview all agree. **Pinned:** a new `serde_json::to_value(&view)` assertion in `test_controller` requires `saved_themes[0].name` / `.theme_json` to be object fields, so this can't regress.

### Refuted (verified NOT real — 2)

- **`load_saved_themes` stores disk `theme_json` verbatim (per-entry byte bound not re-applied on load)** — refuted: `Theme` is a fixed-size POD (no `Vec`/`String`), so a deserializable theme is inherently bounded to a few hundred bytes; `load_saved_themes` filters on `serde_json::from_str::<Theme>` success + name length + `take(MAX_SAVED_THEMES)`, which caps count and validates each entry. No unbounded path.
- **`load_all` reads the whole `saved_theme` table with no SQL `LIMIT` before the cap is applied** — refuted: the table itself is bounded by the write path (`save_all` only ever persists the capped in-memory map), the cap is re-applied on load (`take(MAX_SAVED_THEMES)`), and no wrong output arises in any scenario. Adding a `LIMIT` would be cosmetic.
