# Code Review — Batch: remote console thumbnails (86ajtwq28)

- **Scope:** the real fix for owner refine #7 in the owner's actual setup. The operator, audience output, and confidence monitor run as **three processes on one machine** (multiple monitors, **no network**); pressing Next/Go-Live in the operator changes the audience monitor → the operator drives the `selahcue-desktop` output app over the **loopback** control link (`Backend::Remote`). So the composited pixels live in the *output-app* process, and `render_console`'s Remote branch returned `available:false` → the panels showed the reference text. Fix: the output app answers a new **`GetConsoleThumbnails`** request with its real Preview + Live output downscaled to a thumbnail; the `RemoteOperator` fetches it over the same loopback link; `render_console` forwards it to the console canvases. Entirely local. Executed via `/goal` (`TASK-86ajtwq28-remote-console-thumbnails.md`, validator PASS 4/4). `selahcue-lan` + `selahcue-app` + `selahcue-operator`; **additive wire (VERSION 2 unchanged)**, RBAC `Monitor` (read), never changes what is on air.
- **Method:** an adversarial Workflow review (`wf_52c47943-6d7`, **3 lenses** → per-finding refute-by-default verify, ultracode; 6 agents, 355k tokens, 112 tool calls). Lenses: **protocol-additive / no-drift / compat / base64** · **host read-only / no-on-air-change / RBAC / bounded** · **remote-forward / graceful-degradation / lock-safety**.
- **Outcome:** **3 raised → 0 confirmed → 3 refuted.** Each finding was a real observation the verifier determined does not meet the defect bar (a soft-perf note, a within-policy RBAC judgment, and a pre-existing transport property). All three are recorded below with rationale + the seams they point at; no code change was warranted.

## What shipped

- **Protocol (`selahcue-lan`):** `base64` 0.22 dep; `ThumbView { w, h, rgba: String }` + `ThumbView::from_rgba(w, h, &[u8])` (base64-encodes the RGBA for the JSON wire); additive `Command::GetConsoleThumbnails { max_w, max_h }` + `ServerMessage::ConsoleThumbnails { preview: Option<ThumbView>, live: Option<ThumbView> }` (`skip_serializing_if` on `None`). **VERSION 2 unchanged** — existing pinned `Request`/`ServerMessage`/`Command` fixtures are byte-identical (additive internally-tagged variants).
- **RBAC (`rbac.rs`):** `GetConsoleThumbnails => Monitor` — a read, alongside `GetState`/`GetOperatorState`.
- **Host (`selahcue-app/controller.rs`):** `LiveController::apply(GetConsoleThumbnails)` is a **read** (in the no-`state_dirty` set): it clamps `max_w/max_h` to 480×270, thumbnails `presenter().preview_output()`/`live_output()` via the deterministic `FrameBuffer::thumbnail`, and returns `ConsoleThumbnails` via `ThumbView::from_rgba`. No command, no tick — the audience output is untouched.
- **Remote client (`selahcue-app/operator.rs`):** `RemoteOperator::console_thumbnails(max_w, max_h)` round-trips `GetConsoleThumbnails`→`ConsoleThumbnails`.
- **Operator (`selahcue-operator/main.rs`):** `render_console` (async) — Local branch = local FrameBuffers → base64; **Remote branch** = `m.lock().await.console_thumbnails(..).await` → forward the host's ThumbViews as `{available:true, preview, live}`; a transport error → `{available:false}` → the webview text fallback. Removed the now-unused `Backend::console_thumbnails`.

## Findings and dispositions (all refuted)

| # | Lens | Sev | Finding | Disposition |
|---|------|-----|---------|-------------|
| 1 | host | (perf) | The thumbnail box-average downscale runs under the shared controller lock, briefly contending with the audience-render thread. | **Refuted — soft-perf, not a defect.** No on-air change (`thumbnail(&self)` returns a NEW buffer; sources untouched), no panic (dims clamped 1..=MAX_DIMENSION, `u64` sums, `n.max(1)`), no deadlock (one lock, no cycle, always released). The hold is sub-ms and **infrequent** (the operator fetch is debounced + sig-deduped, only on state change), so at most one 60 fps audience frame is delayed <1 ms — imperceptible. The optimization (downscale outside the lock) is marginal + more invasive; the current design is correct. **Seam:** a future latency-sensitive path could clone-then-downscale off-lock. |
| 2 | host | (policy) | RBAC `Monitor` can pull PREVIEW-output pixels (rendered not-yet-live lyric content), more than the metadata `Monitor` saw before. | **Refuted — within the documented `Monitor` scope.** `Permission::Monitor` is defined as *"Observe live/preview state"* (rbac.rs), so preview observation is inside its purpose; the change maps `GetConsoleThumbnails` to `Monitor` exactly like `GetState`/`GetOperatorState`. There IS an incremental data difference (rendered pixels vs metadata), but the audience output is public and the confidence monitor already shows preview-class content; a Viewer observing the output thumbnail is monitoring, not exfiltration. **Decision recorded:** acceptable; a future tighter policy (a separate `ObservePixels` permission) is a seam if a deployment needs it. |
| 3 | remote | (transport) | `render_console`'s Remote branch holds the `Backend` mutex across a **timeout-less** host round-trip — a stalled host could wedge every operator command. | **Refuted — pre-existing + correct + unsafe to "fix" naively.** Holding the tokio async Mutex across the `.await` is **mandatory**: the `ControlClient` owns one WebSocket with a sequential `next_id`, so releasing the lock mid-round-trip would let commands interleave and **mismatch replies** — a real bug. The missing per-command timeout is **pre-existing and identical across every `Backend::Remote` arm** (view/next/go_live/blackout/…) and the always-on `view` poll; `render_console` follows that verbatim. The batch's target is **loopback**, which cannot silently drop (a dead peer RSTs → `recv_json` returns Closed → `Err` → `{available:false}` text fallback, which works). A naive `timeout` that drops the future mid-recv would leave the sent request's late reply to be mis-read by the next command (desync). **Seam:** a proper per-command timeout **with resync/close** belongs at the `ControlClient` transport level and applies to all commands (the deferred WiFi/mobile-peer hardening), not this batch. |

**0 confirmed defects.** The protocol lens confirmed the addition is byte-additive (no fixture drift; `base64` correct — 8 bytes → 12 chars; `w·h·4` matches the decoded length the webview guards). The graceful-degradation path (transport error / `None` frame → text fallback) is correct.
