## What shipped

- **Engine (`raster.rs`):** `FrameBuffer::thumbnail(max_w, max_h)` — a deterministic integer **box-average** downscale (each destination pixel = the integer mean of its source block), aspect-preserving, **never upscales** (a buffer already within the bound is returned unchanged), `max` clamped to `1..=MAX_DIMENSION`, `u64` channel sums (a 1×1 target covers the whole image). Pure integer → byte-identical cross-OS (NFR-014).
- **App (`operator.rs`):** `OperatorShell::console_thumbnails(w, h)` reads `presenter().preview_output()` / `live_output()` and thumbnails them — a **read-only readback**: it applies NO command and does NOT tick, so rendering the preview can never change what is on air. The frames are whatever the last action/refresh composited — the true audience pixels (incl. blackout / the live scene).
- **Operator host (`main.rs`):** `render_console(max_w, max_h)` command → `Backend::Local` returns `{available:true, preview:{rgba,w,h}, live:{rgba,w,h}}` (base64 RGBA, `max` clamped to **480×270**); `Backend::Remote` returns `{available:false}` — the true pixels live on the remote host and are not on the control wire (streaming them is a documented seam), so the UI keeps its text fallback.
- **Operator webview (`dist/`):** a `<canvas>` per panel (`aria-hidden`; the title/cap carry the accessible label); `renderConsole()` (debounced 120 ms, gated on the console surface being active) invokes `render_console` at the panel's pixel size, blits via `ImageData` with a `bytes.length === w*h*4` guard, and sets `.has-render` (canvas shows; title/cap become a compact OBS-style overlay label). `available:false` / error / a malformed payload → `setConsoleRender(false)` text fallback. A **signature dedup** skips re-fetching an identical frame on the 1 s poll; `showSurface('console')` always renders on return.

## Findings and dispositions

| # | Lens | Sev | Finding | Disposition |
|---|------|-----|---------|-------------|
| 1 | frontend | (raised) | Sig-dedup omits per-item `slide_index` + `theme`, so the monitor freezes on slide-advance / per-item-theme changes. | **Refuted — already fixed.** I added `view.items` (which carries `slide_index` + per-item `theme`) to the signature *before* the verify stage, precisely so a within-item change refreshes the panels. The verifier confirmed the current code includes `view.items`; no stale panel. |
| 2 | frontend | (raised) | Sig includes `view.timer`, forcing an identical ~1.4 MB `render_console` round-trip every second while a timer runs. | **Refuted (sub-defect) — acted on.** Verified independently: the countdown composites onto the **stage/confidence monitor only** (`controller.rs` `tick`: *"NOT on the audience/program output"*), never `preview_output()`/`live_output()`. So `view.timer` in the console signature caused a redundant every-second re-render with byte-identical pixels. **Removed `view.timer` from the signature** — a clean efficiency win with no downside (the preview/live pixels genuinely don't change when the timer ticks). |

**0 confirmed defects.** The read-only lens confirmed the readback never mutates on-air state (no command, no tick; the sync command clamps + can't deadlock — it holds the std lock only synchronously, unlike the earlier `pick_image` async-required case). The thumbnail lens confirmed the downscale is overflow-safe for any `u32` size (`u64` sums; `max` clamped; aspect `max(1)`), deterministic, and correct.
