# ADR-0031 — Cross-machine deck identity: a uid per presentation, translated at the machine boundary, failing closed to "missing"

- Status: Proposed (until the Software Architect and Security Reviewer sign; implementation in ClickUp 86ak196cr, consumer is FR-139 plan-bundle import, 86ak0qn15)
- Date: 2026-10-24 (revised after review round 1)
- Confidence: High that the failure is real and that failing closed is the right default. Medium-high on where the translation happens (see "Options considered"). The residuals are listed under "Known limits".
- Owner: Backend Engineer, for Software Architect and Security Reviewer review
- Relates: ADR-0024 (presentation import; its decision 5 already keeps `DeckId` stable on `Replace` for the same reason), ADR-0020 (authored decks, plan content links), ADR-0007 (persistence)
- Domain: `docs/product/DOMAIN-library-organisation.md` section 9.2 (`FINDING-LIB-07`, `RULE-LIB-XFER-01`, `RULE-LIB-MIG-03`)
- Goal: `docs/delivery/goals/86ak196cr-deck-identity.md`
- Follow-ups: 17tnw2b9ahh (media ids are per-library too), 17tnw2b9ahj (carry the uid on the plan link), 17tnw2b9arx (deck numbers are reused after a restart), 17tnw2b9ary (leftovers from the PR #222 review), 17tnw2b9awr (a deck whose name disagrees with its row key overwrites the real row on an ordinary action)

---

## Context

A service-plan item links a presentation as `ItemContent::Deck { deck_id, slide_count, label }`. `deck_id` is `DeckLibrary::mint_id()`: a counter that starts at 1 in every library and only counts up inside it. Two machines therefore hand out 1, 2, 3 to unrelated presentations.

Nothing in the product moves a plan between machines today (the run-sheet `ImportPlan` command carries kind, title, owner and seconds, and no content links; the FR-139 bundle is unbuilt), so the defect is latent. The first feature that does carry a plan across a machine boundary switches it on: a bundle exported on machine A holds `Deck { deck_id: 3 }`, and importing it on machine B, whose own deck 3 is something else, shows that other deck on the audience output with no marker of any kind. The failure is silent and lands on the highest-consequence surface in the product, which is why `RULE-LIB-XFER-01` says a cross-machine deck reference must be resolved by something globally distinguishable, or must fail closed to the missing-content state.

## Decision

1. **Every presentation has a `DeckUid`**: 128 random bits written as 32 lowercase hex digits, stored **with the deck** (`SlideDeck.uid`, an additive optional field in `deck_json`, omitted from the JSON while unset). The library mints one when a deck is **created**, **duplicated** (a duplicate is a different presentation, so it never shares its source's), or **adopted**. `adopt` and `adopt_with_policy` **always mint a fresh uid for a deck they add**, whatever uid the incoming deck carries (see "A uid is a claim"); `Replace` adds no deck and keeps the target deck's own uid instead. Renaming, editing, replacing (ADR-0024 decision 5) and undo-delete keep the deck's uid; `store()` re-applies the library's own uid over whatever the editor handed back.
2. **The local number stays the local handle.** Plan rows, the wire protocol, the webview and the mobile app keep using `deck_id` exactly as before. Nothing about how a plan is stored or sent between the operator and the host changes.
3. **The number never crosses a machine boundary through the seam.** A deck link leaves a machine as a `PortableDeckLink { uid, label, slide_count }` (`selahcue_core::deck_ref::export_deck_link`, via `DeckLibrary::export_link`). On the receiving side `import_deck_link` (via `DeckLibrary::import_link`) asks the receiving library "which of your saved presentations has this uid?" and binds the link to **that** deck, or, if there is none, to `UNRESOLVED_DECK_ID` (`0`, a number no library ever assigns) with the exporter's last known name. The operator then sees the existing missing-content state (FR-007 / FR-070) with the presentation's name, before the service. The exporter's local number is not an input to the import function, so a caller of the seam cannot use it by mistake.
4. **Fail closed in every non-match case**: absent uid (the exporter could no longer identify the deck), malformed uid (wrong length, upper case, non-hex, all zero, hostile length), a uid the library does not hold, a deck that is only in the undo-delete trash, or a library that answers with the sentinel.
5. **Legacy decks are backfilled once.** On load, a deck with no valid uid, or whose uid duplicates another deck's, is given a fresh one. It is written back **only to the row it was read from, and only when that row's key equals the deck's in-memory name** (compared exactly: a key that differs only by case or a space is a different row). The write is the whole deck as it now is in memory, so a row whose key equals its *healed* name (for example "Zed (2)" holding a deck named "Zed") is written with that healed name and number as well as the uid; that is harmless, because it is the deck's own row. `save_one` upserts by the deck's name, so for a row whose key disagrees with the JSON name (a restored, hand-edited or older-build database) or whose name had to be healed in memory, the write would overwrite some other presentation's row or create a second row. Such a deck keeps its identity in memory and is re-identified on every launch until the row is repaired. The backfill stops at the first failed write (a locked or read-only database) and retries on the next launch. No schema change for the identity itself: the field lives in `deck_json` next to the `id` that already lives there. (The deck-number high-water mark of limit 4 is a separate, later schema change: v25, 17tnw2b9arx.)
6. **Identity is stable from the second launch**, with three exceptions that each get a new identity on every launch until repaired, and so export links that fail closed: a row whose name had to be healed in memory, a row whose key differs from the name inside it (both decision 5), and any launch on which the backfill gave up after a failed write.

## What this does and does not enforce

- **"Unrepresentable" holds only for callers that use the seam.** `ItemContent::Deck { deck_id, .. }` is still publicly constructible and `DeckLibrary::get(DeckId)` still resolves by number, so code that carries a number across machines and looks it up locally is still wrong in exactly the old way. `characterisation_lookup_by_number_alone_still_shows_a_different_presentation` keeps that behaviour pinned (it asserts the bug and will go red if lookup by number is ever made safe).
- **No production path carries a uid-bearing deck to another machine today.** `ImportItemView` carries kind, title, owner and seconds only; the domain doc (section 9.1) says the FR-139 bundle does not carry decks; there is no deck export. So until a feature exists that carries decks, **every cross-machine deck link imports as missing**, which is the safe direction. Ticket acceptance criterion 3 ("where the same presentation genuinely travels with the plan, the imported item resolves to it") is therefore **DEFERRED, not met**: it is proven only in-process, by the two-library tests that move a `SlideDeck` between two libraries through `adopt_trusted_identity`. It becomes real when a deck-carrying feature lands and makes the trust decision below.

## A uid is a claim

A uid is an **unauthenticated claim**, not proof that two decks are the same presentation. Whoever writes a file can put any uid in it, including one that belongs to a presentation at another church, and the first deck in a library to hold a uid is the one a link for that uid binds to. "The wrong presentation cannot be reached" is true only between honest parties.

- `adopt` and `adopt_with_policy` therefore ignore any uid the incoming deck carries and mint a fresh one, so no deck can pick its identity through them (tested for `adopt`, `KeepBoth`, `Fail` and `Replace`; `Replace` keeps the target's).
- `DeckLibrary::adopt_trusted_identity` is the one entry point that keeps a valid, free incoming uid (so the same presentation can keep its identity as it travels). **No ingress calls it today, and it is compiled in tests only (`#[cfg(test)]`)**, so a production caller fails to compile until the change that records the trust decision (who may assert "this is presentation U") lifts the gate. The gate was verified by adding a call in `main.rs`: `no method named adopt_trusted_identity`.
- The uid is random 128-bit data. It carries no machine, user or time information, is never logged, never shown, never sent to the webview or over the LAN, and **does** travel in exported bundles. It is neither secret nor a credential, and must not be treated as either.
- Why 128 random bits in a custom 32-hex form rather than a UUIDv4: 128 random bits give collision odds at least as good as a UUIDv4's (a v4 has 122 random bits; both are negligible across all installs and all decks that will ever exist) with no version/variant bits to special-case and no UUID crate in the supply chain (NFR-027); the canonical form is one spelling, so equality is byte equality.

## Options considered

- **(Chosen) Identity in the library, translated at the boundary.** Plan storage, wire and webview stay byte-identical, so every plan that exists today keeps opening and resolving to the same decks on the machine that made it (acceptance criterion 4) with no migration of plan rows and no change to the cross-language wire fixtures. The guarantee is concentrated in one pure function that the future bundle import has to call.
- **Carry the uid in `ItemContent::Deck` and resolve by uid everywhere.** Strongest against a path nobody has thought of (a copied database, two operators on one host), but it touches the plan codec, the wire (`ContentLinkView`), the Dart model and its byte-pinned fixtures, and about ten resolution sites in the webview (`planDecks.some(d => d.id === link.id)` and its neighbours), each of which would have to be right for a wrong deck not to reach the audience. Rejected for this ticket as a large, risky change to the live path; tracked as 17tnw2b9ahj so the choice is visible.
- **Content hash as the identity.** An edit changes the hash, so a deck would stop matching its own links the moment someone fixed a typo. Rejected.
- **Fail closed only (a bundle never resolves a deck link).** Safe, but the same presentation could never resolve. Rejected as the end state; it remains the behaviour for every case the uid cannot prove, and it is the actual behaviour until a deck-carrying feature exists.
- **Name matching.** Names are operator-typed, uniquified with a "(n)" suffix, and unrelated across churches. A name match is exactly the silent wrong deck. Rejected; the name travels only as the label that describes a missing deck.
- **Not weighed in the first draft, weighed now:**
  - *Mint lazily, at first export.* No write at load, no backfill, and a deck that is never exported never gets an identity. Rejected because it makes the identity depend on the exporter having run, so a presentation exported from two machines before either ever saw the other's decks would carry different identities with no way to tell later, and because the first export would have to write during an operation the operator thinks of as read-only.
  - *A dedicated column on the `deck` table.* An older build's upsert (`save_one`) touches only `deck_json`, so a column would survive a downgrade-then-upgrade, which a field inside `deck_json` does not. This is the better storage if downgrades matter. Backfill-now into `deck_json` was chosen because it needs no schema change, rides every existing persistence path (rename, replace, restore) for free, and the failure on downgrade is the safe direction (below). If downgrade-then-upgrade turns out to matter in the field, moving the uid to a column is a forward-only migration that can read the field out of `deck_json`.

## Persistence and compatibility

- `deck_json` gains `"uid":"<32 hex>"` for decks that have one. **This departs from the rationale of `RULE-LIB-MIG-03`** (the rule is literally about grouping data; its reasoning, domain doc line 263, is that metadata an older build must not silently lose should not live in `deck_json`, because an older build re-serialises the deck without fields it does not know). The consequence here is different in kind from filing data and is safe, but it is real: after a downgrade-then-upgrade the deck gets a **fresh** uid on the next load, so **every link exported before the downgrade imports as missing, on the downgraded machine itself**, which no longer holds the old uid. Fail closed, never a wrong deck.
- No SQL migration: the `deck` table is unchanged (name primary key, opaque `deck_json`). The "migration" is the load-time backfill (decision 5), covered by an equivalence test over legacy rows that compares every stored deck whole except for the added uid (and, for a row whose key equals its healed name, the healed name and number; see decision 5).
- `serde`: the uid is read leniently. A uid that is not a string, or not a valid uid, loads as "no uid" and is healed; it does not cost the deck. This covers a damaged **value**. Damage at the JSON level (a lone surrogate escape, a duplicate `uid` key, a number like `1e999`, nesting deeper than 128) still fails the whole row, exactly as the same damage in `name` does; the library skips a row it cannot read, as it always has.

## Consequences

**Positive.** The wrong-presentation failure becomes unrepresentable for callers of the seam; the fix does not touch the live path; local behaviour is byte-identical; FR-139 has a single, tested function to call and a stated test-matrix requirement (a populated destination whose numbering overlaps).

**Negative / watch.**
- A uid is one more field to carry correctly. The library is its authority: `store()` re-applies the library's uid, `duplicate()` always mints, and `uid_held` counts the undo-delete trash so a restored deck cannot end up sharing an identity.
- `getrandom` (already in the dependency tree for the transcript key) becomes a non-optional dependency of the operator.
- First launch after upgrade writes one row per legacy deck (about 0.2 s for a few hundred decks in debug), once. If the database is locked, the backfill gives up after the first failed write, so the cost is one busy-timeout wait (about 5.3 s) on that launch, not one per deck.

## Known limits (deliberate, tracked)

1. **A link that imported as missing does not remember the uid.** It carries the label only, so re-exporting it to a third machine that does hold the deck cannot match it (pinned by `a_link_that_imported_as_missing_stays_missing_when_exported_onward`), and it cannot heal if the deck arrives later. It stays missing, which is the safe direction. Carrying the uid on the item is the "uid everywhere" option above (17tnw2b9ahj).
2. **Paths that move a plan without going through the seam** (copying the SQLite file to another machine; two operators with different libraries attached to one host) still resolve a link by local number. The ticket classes the first as unsupported. The second may be live today: the LAN server accepts up to 128 connections, so a host could in principle serve operators with different libraries; decks are operator-owned by design and 86ajy02zq is the different question of who resolves them. Both are closed by the "uid everywhere" option (17tnw2b9ahj) if the product supports them.
3. **Media has the same per-library numbering** (`ItemContent::Media { media_id }`). Same rule, same hazard, out of scope here: 17tnw2b9ahh.
4. **Deck numbers were reused after a restart; fixed by 17tnw2b9arx, with the limits below.** `next_id` was recomputed at every load from the surviving decks and the undo trash is memory-only, so a number retired by a delete could be handed to a different deck later, and a plan link that still held it resolved to that deck (and `export_link` carried its uid under the old label). The library now persists a **high-water mark**, the highest deck number ever written for a deck on this database, in one row (`deck_id_counter`, schema v25, `selahcue-data`): every deck write raises it in the same transaction as the row (`deck_repo::save_one_numbered` / `rename_one_numbered`), only through SQL `MAX`, with a trigger that refuses an UPDATE that would lower it; deleting a deck never touches it; `next_id` starts at `max(highest surviving, mark) + 1`; and a load raises a missing or behind mark to the highest surviving number and never lowers it. A store from before the mark loads unchanged (no row reads as 0). A plan item whose deck was deleted therefore keeps pointing at a number nothing will ever hold again and shows the existing "Presentation missing" state, after a restart and after new decks are created. What this does **not** do: it does not stop two operators sharing one database file from each holding a stale in-memory counter (limit 6), it does not apply to a database that is copied to another machine (limit 2), and an older build cannot open a v25 database (`SchemaTooNew`, as with every migration). Chosen over "resolve local plan links by uid" because that is the larger "uid everywhere" change (17tnw2b9ahj, still open) and this closes the single-machine hole with no change to plan storage, the wire or the webview. Tested in `deck_number_tests.rs` (each test fails with the mark removed) and in `selahcue-data/tests/test_deck_repo.rs` / `test_db.rs`.
5. Looking a uid up is a scan of the library (bounded by the number of decks, a few hundred at most) and the backfill's held-uid check is quadratic in the number of decks to heal; a bundle holds at most `MAX_PLAN_ITEMS` links, so an import is bounded work. A set-based check is tracked in 17tnw2b9ary.
6. Two operator processes on one database (there is no single-instance guard) make the backfill last-writer-wins. That fails to "missing", never to a wrong deck. The deck-number mark does not close this: each process seeds its counter at load, so a second process that started before the first one's later creates can issue a number the first already used (two rows, one number; the next load renumbers the duplicate). Re-reading the mark at every mint, or a single-instance guard, would close it; neither is done.
7. **A deck whose name disagrees with its row key overwrites the real row on an ordinary action** (for example leaving the deck at startup stores it by name). This predates this change and is independent of identities; the backfill deliberately never writes such a deck (decision 5), but the library's ordinary store path still does. Tracked as 17tnw2b9awr.

## Contract for FR-139 (86ak0qn15)

- Export every deck link with `DeckLibrary::export_link`. **Never write `deck_id` into the bundle.** The bundle format has no field for a local deck number.
- Import every deck link with `DeckLibrary::import_link`, then set it with `ServicePlan::set_item_content`. Never construct `ItemContent::Deck` from a bundle field. A test must fail if a bundle parser references a local deck number.
- **Clear an item's content before setting an imported link.** `set_item_content` carries the previous label forward when the new one is blank and the deck number matches; the fix in this change stops that for the unresolved number, but a clean `set_item_content(item, None)` first removes the dependency altogether.
- **The missing-state text is wrong for imported links.** The webview describes a missing deck as "was deleted from the library" (`app.js`, plan item card and inspector). For a link that imported as missing the honest text is "not in this library"; the FR-139 UI work must distinguish the two.
- **Bundles that also carry the deck itself** (a future feature; see "A uid is a claim"): bind the bundle's links to the deck adopted **from that same bundle** before any pre-existing local holder of the uid; the import preview names the local deck each link bound to and flags any embedded deck whose uid was already held; and the caller must have made the trust decision before lifting the `#[cfg(test)]` gate on `adopt_trusted_identity`.
- The import preview reports how many presentations are not in this library (`DeckLinkMatch::NotInLibrary`).
- The test matrix must include a **populated destination whose numbering overlaps the source** alongside the clean-install case. `identity_tests.rs` in `selahcue-operator` is the worked example, and it refuses to carry a media number (17tnw2b9ahh).
- FR-139's criterion "export, import, export produces an equivalent bundle" cannot hold for a link that imported as missing (it keeps only its name; limit 1) and must be qualified.
