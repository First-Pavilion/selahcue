# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SelahCue — a cross-platform church presentation & ministry-assistance app. The repo is split:

- `implementation/` — production code, one self-contained root per platform: `desktop/` (Rust workspace — the only fully buildable platform; see `implementation/desktop/CLAUDE.md` for its build/test commands and crate architecture), `mobile/` (Flutter controller app in `mobile/selahcue_controller/`), `web/` (placeholder).
- `docs/` — all planning/architecture/design/delivery artefacts. Decisions live in `docs/architecture/adr/` (ADR-0001…0019) and `docs/decisions/DECISION-LOG.md`; the master architecture is `docs/architecture/ARCHITECTURE.md`; the PRD is `docs/product/prds/SelahCue-PRD.md`; UI/UX specs are in `docs/design/` (Design 2.0 handoff: `DESIGN-2.0-HANDOFF.md`).
- ClickUp is the delivery source of truth; `docs/delivery/BUILD_STATE.md` is a lightweight pointer (Build Control task `86ajnx548`). Work lands in review-gated batches; each batch gets a `docs/delivery/CODE-REVIEW-batch*.md`.
- **Not in the repo**: the agent role skills and their shared process contract are user-level Claude Code configuration (`~/.claude/skills/`, `~/.claude/team/`). That contract is where the ClickUp discipline above is actually specified — read it before running a role skill. Any in-repo `.claude/` is gitignored, unauthoritative and absent from a fresh clone: don't hunt there for skills, and don't recreate it.

## Commands

The root `Makefile` wraps all the manifest paths and feature flags — prefer it. `make` alone lists all targets. Desktop-specific build/test commands and crate architecture live in `implementation/desktop/CLAUDE.md`.

**A future AI (or other off-by-default) feature that fails to reach `make launch`/`make operator` fails a build, not a checklist.** `scripts/check_launch_reachability.py` asserts `make -n launch`/`make -n operator`'s resolved `--features` list is a superset of the Cargo features tagged `# LAUNCH_REACHABILITY: REQUIRED` (currently `dev-keys`, `openai-notes`, `cloud-stt`) across every crate the dev-launch path builds directly (`selahcue-operator` AND `selahcue-desktop` — the first cut only read the operator's Cargo.toml, itself caught in review as a fourth near-miss of the same bug class, 86akd10dq) — wired into `make ci` and CI. The registry is no longer a hand-maintained list in the script (that was the shape of the second time this bug happened — 86akby7th's `cloud-stt` shipped invisible because the script predated it and nobody edited a separate file to register it, 86akd10dq): every non-`default` feature in each registered crate's `[features]` table must carry a `LAUNCH_REACHABILITY: REQUIRED`/`AUTO`/`OPT-IN` tag AND a `RELEASE: SAFE`/`UNSAFE` tag in its own comment block, and the script hard-fails if either is missing or unrecognised — a new feature cannot land without recording both decisions, in the same file and the same review a reviewer is already looking at. The `RELEASE: UNSAFE` set is cross-checked against the Makefile's own `RELEASE_UNSAFE_FEATURES` registry (the actual `release-ai-guard` enforcement mechanism) — including refusing outright if that registry is assigned by more than one line of any of the ENUMERATED assignment shapes (`:=`, `+=`, `?=`, `!=`, plain `=`, an optional `override` prefix, any leading indentation) — GNU Make's semantics would otherwise let a later, weaker reassignment silently override at the guard's own position while this check kept reading only the first, `:=`-shaped, unindented one (Sana found the first gap live; Quinn and Sana each found a further spelling the fix still missed, `=` and indented `:=`, before the check was broadened to cover those enumerated shapes). Text analysis stops there by design — `export RELEASE_UNSAFE_FEATURES := ...` and a `define ... endef` block are genuine further weakenings the regex does not enumerate and cannot chase completely — but the executable probe below catches every one of them anyway, because it tests the guard's EFFECT rather than the TEXT that produced it: Sana proved live that both `export` and `define` still trip the probe (`make release-ai-guard RELEASE=1 OP_FEATURES=cloud-stt` genuinely stops refusing) even though they evade the regex. That behavioural backstop, not an exhaustive spelling list, is what actually closes this. The check also refuses to print success at all if an `UNSAFE` tag lands on a crate with NO Make-level guard behind it, or on a crate whose claimed guard has never been proven to actually refuse anything: `release-ai-guard`'s membership in that registry and its refusal (against EVERY `UNSAFE` token for the crate, not just one — a partial weakening that spared one token used to pass) are exercised by real, no-build `make` invocations as part of this check, not merely asserted. See `scripts/check_launch_reachability.py`'s module docstring for the full reasoning, including why the crate list and the Make-target list stay hand-maintained (with automatic drift detection against the Makefile's own structure) rather than derived. `.github/pull_request_template.md`'s "Feature-flag reachability" checklist complements this as a human prompt; it is not the control, since an unchecked box blocks nothing on its own.

**A fresh clone or `git worktree` needs one more step before `selahcue-operator` compiles at all.** Its build script (`tauri-build`) requires two files to exist on disk — the `externalBin` sidecar (`binaries/selahcue-output-<triple>`, `.exe` on Windows) and `binaries/Processing.NDI.Lib.x64.dll` — and `binaries/` is gitignored (`selahcue-operator/.gitignore:11`), so neither is ever tracked. A fresh worktree (the isolation the operating contract requires for every ticket) therefore has neither file, and `make ci`/`check`/`clippy`/`operator`/`build-operator`/`test-stt-real-model` (and anything that depends on them, e.g. `make launch`) dies on this crate with `resource path 'binaries/selahcue-output-<triple>' doesn't exist` before reaching any Rust gate that the diff actually touched. Those targets now run `make stage-operator-binaries` first, which creates empty placeholders for whichever of the two files is missing — the same fix `.github/workflows/ci.yml`'s own "Stage Tauri sidecar/resource placeholders" step applies for CI. That target is **create-only** (`[ -e "$file" ] || : > "$file"`) and must stay that way: one of the two names, `Processing.NDI.Lib.x64.dll`, is the real NDI SDK redistributable an owner vendors by hand (`scripts/fetch_ndi_sdk.sh`), never built by this repo — on a machine that already has it staged, an unconditional `: >`/`touch` would truncate (`: >`) or needlessly dirty (`touch`, which only bumps mtime) it, and git cannot recover a gitignored file if the former happens silently. Never drop that existence guard. 86akc2kmh. **The same fresh worktree also needs `make marketing-install` (`npm ci` in `implementation/marketing`) before `make ci` or `make marketing-check`:** `node_modules/` is gitignored too, and the marketing gate refuses to run against a missing or stale install rather than installing for you, so without it `make ci` stops at that line with an actionable message.

## Conventions and traps

- The LAN wire protocol is contract-tested **cross-language**: JSON fixtures in `implementation/mobile/selahcue_controller/test/models/protocol_test.dart` are pinned byte-for-byte by `selahcue-lan/tests/test_protocol.rs` (`wire_fixtures_are_stable_for_cross_language_clients`). Change both sides together.
- Memory must stay bounded: no unbounded queues/caches/logs; new buffering code gets a bounded-memory test — one that actually bites. Methodology and worked examples are in `implementation/desktop/CLAUDE.md`.
- A SelahCue "theme" is a slide-design template (typography/background/elements, ProPresenter-style) — **not** a light/dark colour mode. See `docs/design/THEME-MODEL-spec.md`.
- CI (`.github/workflows/ci.yml`) path-filters desktop vs mobile vs api vs marketing jobs and skips docs-only changes (the whole workflow, not even the lint job, so a docs-only change costs nothing). **It also has tiers, and the tier is decided once, in the `tier` step of the `detect changed areas` job** (17tnw2b2nxk): **Linux always** (every pull request and every push to `main`, changed areas only), **Windows weekly or on demand** (the weekly run, Sunday 03:17 UTC, which also runs every area with no path filter; a manual `workflow_dispatch` with the `windows` input ticked; a pull request labelled `full-ci`; a release tag `v*`), and **macOS local** (it is not in CI at all, see "What `make ci` does not cover" below). Matrices read the result as `needs.changes.outputs.os`; never write `windows-latest` or `macos-latest` into a matrix. `.github/scripts/check_ci_minutes.py` (run by the workflow-lint job) refuses a macOS runner, a literal Windows runner on a pull-request/push/schedule workflow, a tier step that adds Windows where it should not (it executes the real step for every event type), a matrix job the alarm does not know, and a missing cancel-in-progress for superseded pull-request runs. To run Windows on an open pull request: add the `full-ci` label (it starts the run at once; remove it when done, because every later push then runs Windows too) or `gh workflow run ci.yml --ref <branch> -f windows=true`.
- **CI costs minutes (17tnw2b2nxk).** The repository is private on the GitHub Team plan: 3,000 included minutes a month, each job rounded up to a whole minute, Linux x1, Windows x2, macOS x10, and with no payment method every job is **blocked** once the quota is gone (that is what stopped all CI on 2026-10-04). Measured on the 100 runs of 2026-10-02..05: a three-OS run cost a median 241 billable minutes (Linux 35, Windows 44, macOS 155) and the 100 runs cost 12,046, of which macOS was 64%. After the trim a Linux-only run costs a mean 21 (marketing-only 8.5, desktop-only 25, all areas 43) and the Windows legs add about 45 (they stay off pull requests and pushes). That is still about 3.7 days of quota at the pace of those days (39 runs a day), so **do not add jobs, matrix legs, schedules or extra pushes lightly**, and batch pushes to a pull request (a cancelled run still bills what it used). Measure a change the same way: `gh api repos/First-Pavilion/selahcue/actions/runs/<id>/jobs`, duration per job rounded up, times the multiplier. The numbers and the budget model are in the pull request for 17tnw2b2nxk.
- **The Rust toolchain is pinned in `rust-toolchain.toml`, and that pin is the gate.** rustup reads it for every `cargo`/`rustc` call under the repo (including the two out-of-workspace crates), so `make ci` and CI compile with the same compiler *by construction*; `scripts/check_toolchain.sh` then asserts it, and both gates run that same script first. Before the pin existed, CI installed whatever stable was newest at run time while developers ran whatever they had: on 2026-08-18 stable moved 1.97.1 → 1.98.0, the new `clippy::chunks_exact_to_as_chunks` met `-D warnings`, and `main` went red on the next push and had no green run for nine days while `make ci` kept printing ALL GREEN. Bumping the pin is a normal reviewable change — edit `channel`, run `make ci`, fix what the new lints find, one MR for the bump. `.github/workflows/rust-canary.yml` runs the gates weekly against floating stable and files an issue when a future release would break us, so the pin's deliberate lag stays visible. Never set `channel` to a floating value; the check script refuses it.
- **What `make ci` does not cover** — it is the Rust/Flutter gate (plus the marketing and Django API gates) on *one* machine, not the whole pipeline. The two biggest gaps are structural and cannot be closed locally:
  - **One OS in CI, not three.** On every pull request and every push to `main`, CI runs `rust`, `operator` and `operator-native` on **Linux only**. The **Windows** legs run only on the weekly run, a manual dispatch with `windows` ticked, a `full-ci` pull request and release tags, so a Windows-only break (path handling, line endings, the vendored-OpenSSL encryption suite that CI skips on Windows, the MSVC release build) is **first seen there, not on the pull request that caused it**. The weekly result is the `ci` run with event `schedule` (`gh run list --workflow ci.yml --event schedule`); a Windows failure also opens or updates the `ci-red` issue. **macOS is not in CI at all: your local `make ci` on a Mac is the only macOS gate.** `make ci` runs whichever OS you are sitting at, so a macOS-only break (Core Audio, the signed `.app`, WKWebView layout, Metal) is invisible to CI by design.
  - **A different GPU stack.** The ADR-0015 parity oracle runs on **Metal** on a Mac (local `make ci` only), **lavapipe** (software Vulkan) on CI's Linux, and **DX12/WARP** on Windows (weekly or on demand only). A local pass says the CPU rasterizer matches *your* GPU, not that it matches the ones CI uses.

  Beyond those, CI also runs `cargo audit` + `cargo deny` (supply chain), the Playwright **WebKit** engine smoke (`scripts/operator_webkit_smoke.py` — the Blink gate in `make ci` cannot catch a WebKit-only break), `launch-smoke` + `make nfr`, the Android APK compile-check, and `actionlint` over the workflows. `selahcue-stt` (excluded from the workspace) is linted and tested by **neither** `make ci` nor CI (17tnw2b9aaw). Two CI jobs are covered **in part** by `make ci`:
  - **`api (django)`**: `make ci` runs `make api-check` (also runnable alone) — `manage.py check`, `makemigrations --check --noinput` (a model without its committed migration fails), and the pytest suite, the same three commands as the CI job. It runs on **SQLite with the local cache, so the tests that need Postgres or Redis SKIP locally**: the three DEC-004 instance-limit race tests in `tests/test_concurrency_postgres.py` and the real-Redis test in `tests/test_cache_socket_timeouts.py` (`-rs` prints each skip; at time of writing 709 pass, 4 skip, 1 xfail). Only CI's job, with Postgres 16 + Redis 7, runs them. The venv is `implementation/api/.venv`: gitignored, **per checkout** (an editable install points at the tree it was made in, so a venv borrowed from another checkout would test the wrong code — the gate asserts the package imports from this tree), built on first use (needs Python 3.14 on PATH, or `API_PYTHON=...` for any >=3.12, and the network once) and rebuilt when `pyproject.toml` changes. It fails loudly rather than skipping when it cannot run. Takes about 100 s.
  - **`marketing (vue spa)`**: `make ci` runs `make marketing-check` (type-check, lint, node tests, build — the same target the CI job calls), but not the Django-backed `test:mirrors` or the headless-Chrome `test:states`, and it never installs, so a fresh clone or worktree needs `make marketing-install` first (see `implementation/marketing/README.md`).

  What `make ci` still does not do, tracked in 17tnw2b9aax (the remainder of 86ak5rjh7): it is **not path-aware** (it runs every area on every call, so a desktop-only change also pays for the API gate) and it still **aborts at the first failing recipe line**, so a failure in an early gate hides the later ones.
- **A failing run on `main` opens a `ci-red` GitHub issue** (**live and proven end to end** — run `32933626119` on `main` created [issue #6](https://github.com/First-Pavilion/selahcue/issues/6), the `ci-red` label, and the marker, with `DRY_RUN` correctly false; a `workflow_dispatch` off `main` runs the same job under `DRY_RUN` and writes nothing, which is how to rehearse it safely), and it closes only when every job that was failing has *actually reported success again*. It tracks **which jobs** are outstanding rather than one red/green bit, because CI path-filters by area: an api-only push skips the whole desktop matrix, and a naive alarm would read that skip as "nothing failed" and close itself while `main` was still broken. A **skipped** job is not evidence of anything and never clears the alarm. **The same holds for the Windows legs** (17tnw2b2nxk): `rust`, `operator` and `operator-native` are matrix jobs that report one result for all their legs, so the alarm keys them by what they covered. A Linux-only run reports `rust (linux only)` and records the plain `rust` as `not run`; only a run that included Windows can clear a Windows failure, and the weekly run reaches the alarm for exactly that reason. A Windows failure therefore stays on the issue until the next weekly run, or `gh workflow run ci.yml --ref main -f windows=true`, passes, even if it was fixed the same day (about 80 to 90 billable minutes; stricter on purpose). macOS has no job, so its absence is never a failure. Logic and its self-test live in `.github/scripts/ci_alarm.py` (`--self-test` runs anywhere, and runs in CI on every `main` push). The repo has no branch protection available on this plan, so nothing prevents a red commit landing — the issue is the only alarm. While one is open, treat every branch's CI result as unreadable: a real failure cannot be distinguished from the standing one.
- Design-doc validators live in `scripts/` (`validate_prd.py`, `validate_goal_contract.py`, `validate_delivery_plan.py`) — run the matching one after editing those artefacts.
- **Masking still exists locally, but less of it than it used to.** Every `cargo test` line in `make ci` and in CI now carries `--no-fail-fast`, so a failure in one crate no longer hides the *other crates'* test results (measured on the real ubuntu CI run: **51 of 138 test suites** sit at or after the failing binary and never report at all without the flag — do not go looking for a second *failing* binary, there is exactly one). What remains is **line-level**: `make ci` still aborts the target at the first failing recipe line, so a clippy failure there still means the feature-gated suites, operator check, headless webview check and Flutter gate never ran at all. CI no longer has that property — its steps after Clippy run under `if: ${{ !cancelled() }}`. So a green `make ci` line is evidence about that line only; after fixing a failure, re-run the whole target rather than assuming the later gates were reached. Closing the line-level gap is tracked as 17tnw2b9aax.
- **Run one `make ci` at a time in this checkout.** Concurrent Flutter runs race on `implementation/mobile/selahcue_controller/ios/Flutter/ephemeral/Packages`, which `generatePluginsSwiftPackage` deletes and recreates on every invocation. Two signatures — `Waiting for another flutter command to release the startup lock…` followed by a delete failure, and `FileSystemException: Deletion failed, OS Error: Directory not empty, errno = 66` — are **false reds** (never false greens) and pass on retry with no code change. Check for other active sessions and serialise instead of re-diagnosing them.
- **The checkout is shared**: one worktree on `main`, several agent sessions at once, large uncommitted WIP. Check `ListAgents` and declare your file footprint to peers before starting; never commit, stage, stash or revert another session's work; never `cargo clean` or clear target-dir locks to escape a transient failure.
